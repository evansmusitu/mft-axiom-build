## Confirmed consumption-race blocker

In `ledger.mjs` finishHold(), the commit batch updates an open hold conditionally but inserts its debit unconditionally. The JavaScript changes check happens after that batch committed. A concurrent release can win, followed by the losing commit's zero-row UPDATE and successful debit INSERT. The caller then gets hold_race even though its charge persisted.

The independent exact-module/realSQLite reproduction deterministically lets both calls read open, then runs release before commit. Final hold=released, initial credit10 becomes3, usage debit=-7, and the commit caller rejects. See `finish-hold-race-repro.test.mjs` and `finish-hold-race-repro.log`. This blocks commit-versus-release/concurrent consumption acceptance on the unchanged module. Couple debit SQL to the winning transition inside the database operation; post-commit metadata checks are insufficient. Root remains sole implementation writer. Any repair needs exact-source review and realworkerd regression before hosted use.
