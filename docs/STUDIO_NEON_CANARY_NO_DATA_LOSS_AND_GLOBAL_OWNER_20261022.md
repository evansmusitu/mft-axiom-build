# MUSITU Studio V0.3 — Global owner freeze and ephemeral read-only Neon canary
Date: 2026-10-22  |  Scope: isolated source branch, **NOT deployed**

## Two material release-safety defects resolved in source

**Global DO freeze authorization.** The earlier owner-signed freeze required only one matching `owner` membership in the shared Durable Object ledger. Ownership of one project could therefore stop writes for every project in the same DO, including independent tenants. `acquireStudioSourceWriteFreeze()` and `releaseStudioSourceWriteFreeze()` now additionally query the real SQLite ledger within their transaction and require: at least one project, the signed actor is the recorded founder (`projects.owner_sub`) and `owner` member on **every** project, and no owner-role membership exists for any other subject. If the condition fails, no freeze is installed. This is only a *source-level policy*; it does not verify Cloudflare Access tokens itself. A global signed actor assertion is still required from a trusted Cloudflare Worker binding.

**Expiring destination write fence and irreversible canary.** The previous staged `guardedStudioNeonPromotion()` simulated a production switch directly to `NEON_PROTECTED` while only checking the source's short-lived write fence. If a signed-browser proof or target verification wrote to Neon and a later step rolled back to SQLite, those new writes could be lost. Furthermore, successful cutover would leave target traffic active when the short-lived freeze inevitably expired. The candidate now routes **only** to an explicitly labelled `NEON_CANARY_READONLY` backend after authenticated source write-fence AND independently provider-attested target write-barrier checks, with at least 15 seconds left on each fence. A recheck immediately after the CAS and another after read-only browser/target proofs must pass. **Before returning success it always performs and verifies a second CAS back to `SQLITE_DO`**. It never activates production write traffic. Failure to return to SQLite fails critically; ambiguous acknowledgements require route readback and rollback. Canary success reports `promoted:false`, `canary:true`, `route:'SQLITE_DO'`, `write_activation:false`. Lease release follows readback; release failure fails closed. This is an offline dependency-injected coordinator; the callback supplying a real write barrier and the durable routing control-plane have not been implemented.

**Naming and compat:** This is a security-tightening behavioral change to the staged code, not a backwards-compatible production deployment. Existing test-only callback mocks now include `verifyTargetWriteBarrier`; existing test-only target route expectations change from `NEON_PROTECTED` to `NEON_CANARY_READONLY` (temporary), and successful canary ends on `SQLITE_DO`. The existing ledger-attestation.v2 and transfer.v2 receipts remain unchanged. The five-table HMAC source/target reconciliation and freeze epoch validation remain mandatory.

## Current independent scope and precise limitations

Offline red-first regression tests were added for a tenant holding only some projects, third-party co-owner, multiple projects held by the sole owner, missing destination write barrier, barrier expiring after route switch, and inability to restore the SQLite route. Test fixture exercises actual SQLite triggers and transaction semantics, but read-only canary callbacks are simulated.

There is **no live Cloudflare Worker-to-Neon private connection**, no production SQLite export, and no real source+target provider-backed canary, so the function cannot actually execute in production. Signing/verification truth of provider receipts remains the control-plane's responsibility; arbitrary injected `verified:true` must not be trusted. Production SQLite Durable Object has no installed source-freeze triggers and is still live. Source-only changes do not qualify Cloudflare hosted PITR, real R2 asset digest checks or Neon organization-wide *hard* spending controls. Do **not** disable `block_public_connections`, turn on Modal GPU/CPU, or connect a public route to this code to advance tests.

## Required after this change

1. Prove Cloudflare-hosted DO PITR/recovery on a separate isolated restored instance and safe account-level billing enforcement, with identity and audit preserved.
2. Build a private authenticated, owner-only source export under the exact database-global freeze. Never place the customer rows, object bytes, identities or keys in CI artifacts, logs, Git, chat or public Drive.
3. Build independent, persistent provider-backed source/target write-barriers and verify the canary transition uses a truly read-only route; prove postcheck return to SQLite.
4. Verify isolated hosted Neon restore of all *actual* imported records, R2 object metadata + bytes, full HMAC reconciliation and signed Access browser canary while reads remain read-only. Only then design a **separate** guarded write-activation phase, with durable old-source fencing and gapless dual-backend no-lost-write rollback handling.
5. Demonstrate enforceable organization-wide Neon billing controls (alerts are not hard caps) and independent Modal zero-overage protection. Until those are provider-backed, **no production cutover**.

All changes in this note are staged source only. Keep V0.3 SQLite primary, V0.2 Access, Axiom main, original R2, staff identities, provider secrets and CPU/GPU OFF unchanged.
