## Feasibility decision — distinct choices, no silent requirement change

### A. Keep existing G1 wording unchanged (Neon PostgreSQL protected RPC/private route)
**Modal alone: NOT PROVEN FEASIBLE; G1 NO-GO.** Existing `block_public_connections=true` prevents ordinary Internet PostgreSQL clients from reaching Neon. Modal static outbound IP Proxy is **not AWS PrivateLink** and an IP allowlist exception is not the current private-only standard. Modal public/private application endpoints do not confer AWS VPC attachment to the Neon service. Modal i6pn is private networking among Modal Sandboxes/instances in a workspace, not evidence of access to an external Neon AWS PrivateLink endpoint. No supported direct Modal → Neon private interface was established.

Official [Modal pricing](https://modal.com/pricing) lists static-IP Proxy on Team **US$250/month plus compute**; this is incompatible with the owner's US$25 pilot *unless already paid independently*, and would still not meet private-only Neon. Cloudflare's [Workers VPC/private Hyperdrive guide](https://developers.cloudflare.com/hyperdrive/configuration/connect-to-private-database-vpc/) requires `cloudflared` in a network already able to reach the private database. The current cloud/operator account has no verified such network. Therefore strict G1 would still require approved private network access to Neon, through existing attested VPC infrastructure if present or a separately cost-authorized deployment. **Do not pretend Modal removes that dependency.**

### B. Reuse existing Cloudflare + Modal, substitute an internal Cloudflare D1 spending authority (conditional architecture-change candidate)
**Engineering feasibility: PLAUSIBLE, NOT APPROVED, NOT IMPLEMENTED.** Cloudflare source/staging already advertises D1 as its state store. D1's [single-writer execution](https://developers.cloudflare.com/d1/reference/faq/) and documented transactional [`batch()`](https://developers.cloudflare.com/d1/observability/find-expensive-queries/) provide a potential atomic budget reservation/settlement primitive. [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) let existing Workers call a private budget-authority Worker without a public HTTP URL or a new infrastructure provider. This reuses the existing Cloudflare estate, but would require a **new privileged authorization service, migration, reviewed bindings and live deployment** even if no AWS/VPC resources are created. Do not equate existing D1 customer/billing data with a production-grade reserve/settle ledger.

Proposed boundary, subject to independent security design signoff:
1. Only independently authenticated/authorized trusted Cloudflare ingress determines immutable tenant, organization, provider/model and request identity. No caller-controlled tenant IDs, cost overrides or bypass flags.
2. A **single internal, nonpublic spending-control service** exclusively owns access to a reviewed new ledger schema within the *existing D1*. No other paid-serving Worker/Modal job has a D1 write binding, direct vendor key, or private escape hatch. **Cloudflare service bindings do not automatically propagate Cloudflare Access context**: the service must verify trusted principal and request evidence itself.
3. Atomically reserve the **organization-wide and tenant + vendor/model** caps, request-hash dedupe, lock deadline, integer accounting and pending charge hold in one D1 transaction; fail closed on quota, database overload, duplicate, unknown price, ambiguous response, stale/changed claim or interrupted settlement. A cap checked against an async read then updated later is NOT adequate. The counter authority must be singular for every execution route.
4. The paid vendor adapter is inaccessible until a valid signed, short-lived, one-time server-issued admission is checked; real billable provider secrets must be held by the trusted billing-coupled execution service and not an unrestricted public Modal endpoint. Modal can continue providing **mathematical / non-billable compute** over its authenticated transport. If any paid Modal compute route exists, it needs equivalent pre-call protected reservation and proof-bound settle.
5. Independently enumerate all Cloudflare Worker, Queue, cron, retry, legacy, Modal, direct-proxy, admin and repair paths. Prove no path can call OpenAI/Anthropic without central reserve and no privileged database operator bypass. Reject wrong-tenant, stale token, duplicate, budget race, split-brain/failover, crash-before-settlement, overage, delayed pricing and provider-usage tampering.
6. Run real staging tests through at least two live Worker instances/queues using **synthetic provider responses only**, with the central ledger readbacks and D1 exception/rollback cases. Prove operator access controls, backups/recovery, D1 cost ceiling, audit and emergency shutoff. No production or paid upstream until separately approved.
7. An independent security reviewer and the designated operator must **formally approve changing the G1 acceptance contract** from `PostgreSQL SECURITY DEFINER restricted runtime + TLS private Neon origin` to `Cloudflare private budget service + atomic D1 ledger + verified service bindings`, documenting residual risk and the impact of requiring Neon persistence for *other* Phase 2 workloads. Until rebaseline and live evidence, G1 is strictly **NO-GO**.

### C. Cloudflare Durable Objects transactional counter (another conditional variant)
Cloudflare [Durable Objects](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) provide a globally unique, strongly consistent stateful coordination primitive with SQLite storage. A single organization-keyed object could serialize organization and tenant cap changes inside one object, with careful provider identity/charge semantics. This stays within an existing cloud provider but adds a *new Durable Object namespace and billable storage/compute resource*. It is not literally zero new infrastructure. Its audit/security/recovery, org sharding, failover and billing differences need an independent security decision; D1 reuse is generally simpler to evaluate first, given the existing `state:D1`.

## Verdict and required acceptance
**Current strict G1: NO-GO.** Modal's live compute and authentication boundaries are partially verified; **Neon remains private/inaccessible, dedicated runtime SQL roles do not exist, and all-worker PostgreSQL spending enforcement is unproven**.

**Recommended cost-minimizing G1 investigation:** before any AWS spend, independently audit Cloudflare's actual D1 schema, existing Worker service bindings, Modal workspace plan and protected deployment/credential inventory; conduct a threat model for a D1-controlled budget service and request independent written **G1 architecture-equivalence approval**. This might avoid AWS networking **for G1 spending control only**, but it **cannot** be claimed to satisfy the existing Neon-specific private PostgreSQL G1 wording without reapproval, nor does it satisfy other Phase 2 Neon data/restore requirements.

**Hard constraints:** owner US$25/24h remains an unspent ceiling in this review; no new AWS, Cloudflare, Modal, Neon billable resource or subscription; no change to public database blocking or paid provider credentials; source changes/design alone are not G1 acceptance. Other release gates are outside scope.
