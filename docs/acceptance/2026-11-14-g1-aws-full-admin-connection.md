# MUSITU AXIOM G1 — full-capability AWS administration via GitHub environment secrets

**Date:** 2026-11-14. **Status:** UNMERGED SOURCE-ONLY DRAFT, NOT CONNECTED. **User direction:** reusable AWS access with broad administrator permissions, in the same GitHub-secrets workflow pattern as Cloudflare; do not create redundant custom IAM API policies. **Owner-approved financial boundary still US$25 combined AWS+Cloudflare+Neon additional cost, single 24-hour G1 pilot**, with US$20 target and US$5 reserve; reported US$50 AWS credit availability is unverified.

## What this DOES and DOES NOT authorize

- An AWS IAM principal with **AdministratorAccess** may manage nearly all AWS services, subject to account SCPs, explicit denies, permission boundaries, and root-only or other special operations. Full IAM permissions are conferred by the AWS identity, **not** by creating GitHub secrets.
- GitHub Actions can run scripts with that principal **only when the protected GitHub workflow reaches its approved environment**. This first workflow **only calls STS GetCallerIdentity**, silently verifies a valid caller and prints redacted true/false flags. It **does not establish AdministratorAccess**; a second privileged action would require separately reviewed/approved code and a live IAM authorization review.
- The connected ChatGPT GitHub integration can prepare changes and inspect sanitized workflow results, but **cannot directly read AWS secrets or directly invoke arbitrary AWS APIs**, and currently has no first-party AWS administrator connector. Generic arbitrary AWS CLI or shell-string inputs must NOT be exposed through workflow_dispatch. Each later VPC/PrivateLink/Neon provisioning step should be a reviewed, versioned, owner-authorized workflow with preview/plan, rollback, audit and independent acceptance.
- Even if the AWS IAM principal has full rights, high-risk resource deletion, irreversible IAM changes, large cost commitments or changes outside approved G1 scope require their own approval. No scope expansion or change of USD25/24-hour cap is implied by "all permissions".

## Required preflight before any long-lived AWS admin secret

1. **Protect the repository** first: [MUSITU AXIOM rulesets](https://github.com/evansmusitu/mft-axiom-build/settings/rules). As of this audit, there are **zero enforced rulesets** on main. Protect `main` with required PR reviews, required checks, block force-push/deletion, and review changes to `.github/workflows/`, `scripts/`, and `tests/`; prevent admins from bypassing protection if feasible. Verify all rules are active on the target repository. An unprotected public default branch plus long-lived administrator keys is an unacceptable key-exfiltration risk.
2. Open [GitHub Environments](https://github.com/evansmusitu/mft-axiom-build/settings/environments) and create `g1-aws-admin`. Restrict deployments to **protected main only**. Require **an independent reviewer and prevent self-approval or bypass** where GitHub plan supports these features. The first workflow is owner-dispatched, so an independent reviewer must approve deployment rather than the actor approving their own run. **If these protections are unavailable, use GitHub OIDC and short-lived AWS STS role credentials instead of long-lived AdministratorAccess keys.**
3. Reuse an existing **non-root AWS IAM administrative identity**, if one already exists and has an access key whose secret you retained, or create a dedicated AWS IAM principal using AWS's managed `AdministratorAccess` permissions only if the owner explicitly accepts the exposure. No custom policy is required for this bridge. **Never create/use AWS root-account access keys**. Never paste the key values into this repo, GitHub issue, logs or ChatGPT. AWS recommends short-lived role credentials via [federation / OIDC](https://aws.amazon.com/iam/resources/best-practices/) as the better long-term design.
4. Under **GitHub environment `g1-aws-admin` → Environment secrets**, add exact names:
   - `AWS_ADMIN_ACCESS_KEY_ID` = the IAM principal's access key ID
   - `AWS_ADMIN_SECRET_ACCESS_KEY` = its secret access key
   These must **not** be general repository secrets, `g1-aws-readonly` environment secrets, workflow inputs or checked-in files. Restrict which maintainers can modify workflow files and environment settings. Rotate/revoke the admin key and audit CloudTrail usage regularly.
5. Inspect [AWS Billing → Credits](https://console.aws.amazon.com/billing/home#/credits) **inside the authenticated AWS console**, verify the reported US$50 balance, expiration and each intended service's eligibility. Credits do **not** pay Neon/Cloudflare, and do not increase the existing US$25 all-provider pilot maximum. AWS Budgets alerts do not enforce an instantaneous hard billing stop. Set up a human-operated scheduled 24-hour teardown plan and validated forecast before provisioning.
6. Obtain review of draft [PR #239](https://github.com/evansmusitu/mft-axiom-build/pull/239), and then merge workflow source **only once branch and environment protections are verified**. GitHub `workflow_dispatch` can be executed only after the workflow exists on the default `main` branch.
7. Owner selects Actions → **G1 AWS administrator identity preflight (read-only)** → Run workflow → check `confirm_identity_read_only`. A separate environment reviewer approves the pending deployment. Sanitized output indicates only whether AWS caller identity was confirmed; **not** actual permissions, credits, PrivateLink, or G1 acceptance. The connected GitHub tool can inspect the safe run logs.
8. **Only after authenticated read-only verification:** separately review and test a *specific* AWS G1 PrivateLink plan, count current Ohio VPC endpoints/AZs, obtain actual cost estimates, configure TTL/teardown, Cloudflare Tunnel/Hyperdrive operator credentials, keep Neon public access blocked, and obtain actual PostgreSQL TLS/role/cross-worker ledger evidence and independent G1 signoff.

- `tests/test_g1_aws_admin_bridge.py`: 4 local tests. Before implementation: 4 errors for missing source/workflow files; after implementation: **4/4 passed** in local isolated repo layout. This red/green only covers static offline behavior, not remote AWS permissions or real account connectivity.

## Alternative strongly recommended for durable full-capability connection
Use the built-in `aws-actions/configure-aws-credentials` GitHub OIDC pattern with a restricted AWS trust policy matching `repo:evansmusitu/mft-axiom-build:environment:g1-aws-admin`, short AWS STS session lifetime, and an administrator-capable role if required. This avoids storing reusable AWS admin secrets; still requires AWS IAM OIDC identity provider and trust-role setup and protected GitHub source. See [GitHub OIDC for AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws). OIDC may be more setup, but provides less persistent exposure for powerful AWS permissions.
