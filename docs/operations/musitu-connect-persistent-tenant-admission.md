# MUSITU Connect — persistent tenant admission research contract

**22 October 2026. Nonproduction code only. No customer accounts created or
new production endpoint enabled.** This extends the 21 October identity
prototype without replacing the separately authorized production Worker.

## Verified offline contract

- Schema: `infra/connect_customer_registry.sql` defines tenants, hashed
  credentials, daily and UTC-minute quotas, and per-request usage events.
- Module: `connect/customer_admission.mjs`, disabled unless
  `CONNECT_CUSTOMER_RUNTIME_ENABLED` is the string `true`.
- Admission: `reserveConnectCustomerRequest({authorization, scope, env,
  nowMs, requestIdFactory})` accepts only the *route-selected* scope. The
  tenant is derived by a database lookup on SHA-256 of the independently
  issued high-entropy `mct_` bearer, never by trusting a request-body tenant.
- The database binding `CONNECT_CUSTOMER_DB` must be available and have
  Cloudflare D1-style `prepare(sql).bind(...args).first()` methods.
- A single `INSERT ... SELECT ... RETURNING` into usage events is guarded by
  SQLite `BEFORE` and `AFTER INSERT` triggers. Within the one SQLite
  statement, a scoped active credential is required, an active tenant is
  required, one request is recorded, and both UTC-day and UTC-minute counters
  are incremented. A daily limit breach returns `CUSTOMER_QUOTA_EXCEEDED`
  (HTTP-equivalent 429); an exceeded minute limit returns
  `CUSTOMER_MINUTE_QUOTA_EXCEEDED` (also 429). Neither publishes a partial
  event/counter write. Each tenant's limits are explicitly configured in
  its registry record; there is no implicit per-customer production default.
  The SQL trigger also rejects `observed_at` values that are not canonical
  UTC timestamps or that disagree with `utc_day`, preventing mislabeled
  accounting events from bypassing either quota.
- `readConnectCustomerUsage({db, principal, utcDay, nowMs})` reads only the
  admitted, server-derived, frozen principal's tenant. Forged principal
  objects are denied, and the credential is checked again against the store
  during reads.
- Usage event keys are `(tenant_id, request_id)`; replay under one tenant
  fails, while other tenants' records remain separate. The request ID must
  be generated by the trusted server using UUID v4. Do **not** pass a
  customer-supplied ID generator into the runtime.
- Invalid credentials, expired/revoked/suspended tenants or credentials,
  missing scope, invalid source clock and missing database fail closed.
  Error responses omit tokens, hashes, SQL text and other tenants' data.
- Quota is a **reservation per admitted attempt**. It is not confirmed
  billable usage or proof that downstream execution succeeded. The refund,
  cancellation and billing policy is unresolved and must be explicitly
  approved before this interface is made public.

## Additional bounded request-body boundary (22 October 2026)

`connect/customer_payload.mjs` is an **offline-only, non-admission**
request reader intended for a future customer-facing Worker, not an import
or execution path of the currently deployed production service. The proposed
research policy is at most **65,536 raw transport bytes (64 KiB)** for one
JSON object. This is a provisional engineering ceiling requiring product
profiling and security sign-off before external customer use.

The reader rejects unsupported HTTP methods and media types, nonidentity
content encoding, nonnumeric/inconsistent `Content-Length`, actual streamed
bytes exceeding the cap (including UTF-8 multibyte text), invalid UTF-8,
malformed JSON and nonobject top-level values. It checks actual byte count
whether or not `Content-Length` is provided and never returns partial
JSON on rejection. Transport errors are sanitized.

The `node --test tests/connect/test_customer_payload.mjs` regression
suite exercised exact-cap success, streamed oversize refusal, declared-size
mismatch, compressed encoding refusal and malformed-data behavior. The
test-first red checkpoint was GitHub Connect CI run `39748095502`:
the disabled implementation failed all 10 new tests while 30 existing
Node tests passed. After implementation, the same expanded Node suite passed
**40/40** in GitHub Connect CI run `39748278360`.

A second offline test surface composes the same transport-reader module
into an isolated Cloudflare **workerd fetch()** handler through
`tests/connect/test_customer_payload_workerd.mjs`. The GitHub run
`39748986714` passed **2/2** workerd HTTP tests (valid JSON and oversized
UTF-8 request) alongside the **13/13** reference SQLite and **2/2**
local D1 tests. Workerd simulation is not a hosted Worker or a real D1
account. No customer-facing routes or authentication settings were changed.

**Not established:** duplicate-key rejection, schema-level Mining semantics,
authenticated tenant admission, real D1 metering, clock/CPU limits, global
in-flight request limits, customer billing and security ownership. Future
routing must first authenticate and reserve the request using the trusted
tenant context, then apply the bounded transport reader *and* the already
qualified per-operation semantic validator. A malformed request may still
consume a quota reservation; this must be approved as a product policy.
No new customer API should be deployed merely because these unit tests pass.

### Local Cloudflare D1 runtime qualification — 22 October 2026

The isolated `tests/connect/test_customer_d1_local.mjs` suite runs through
Cloudflare's **Miniflare/workerd local D1 binding**, rather than only the
Node SQLite compatibility shim. The feature-only GitHub workflow
`.github/workflows/musitu-connect-d1-local.yml` installs exactly
`miniflare@4.20260730.0`, with a supported local workerd compatibility
date of `2026-07-01`, no Cloudflare API token, no production bindings,
and no external customer records.

Verified branch CI: run
`39741990668` at commit
`bfe411843c67d9b2e499beb350ea2821a166bfb5`.
The successful job separately executed **13 local SQLite reference tests**
and **2 local workerd-backed D1 tests**, all passing. The local D1 tests
checked tenant-separated hashed credential admission, independent scopes,
atomic daily/minute quota reservations, frozen principal usage reads,
revocation, and a burst of concurrent local requests.

Two portability issues surfaced through actual red test runs and were
corrected: the pinned stable workerd binary requires an earlier
compatibility date, and D1's `exec()` requires each schema DDL block,
including each full SQL trigger, to be supplied as a complete statement.
The shared schema also no longer embeds a Node-only foreign-key setup
pragma; SQLite reference fixtures explicitly enable foreign keys and D1
enforces them by default.

**This is a local simulation, not an account-backed Cloudflare D1 staging
database.** It does not verify remote replica consistency, multi-region
concurrency, production identity issuance, customer isolation under
real network traffic, or a deployed staging Worker. No actual D1 database,
Cloudflare binding, secret, commercial account or production route was
created or mutated.

**These tests do not constitute a Cloudflare D1 staging qualification.**
In particular, production D1 prepared-statement `INSERT RETURNING` behavior,
atomicity under *cross-region concurrent Worker invocations*, durability,
consistency of revocations, platform rate limits and quota alerts must all
be verified with isolated nonproduction infrastructure before deployment.
A local `Promise.all` test over one SQLite connection is not a load test.

## Release-gate separation and operational signoffs

The original static, secret-JSON customer identity prototype
(`connect/customer_identity.mjs`) is not a provisioning path. This
SQLite/D1-compatible module is an *alternative preparatory persistent store*
implementation, not an approved migration plan or product switch.

Before onboarding a real customer, engineering must implement and approve
credential issuance, storage and rotation; tenant-aware data access beyond
usage aggregation; input-byte and CPU limits; real-D1 verification of per-minute and daily quotas;
secure customer operations; audit retention/deletion; support ownership;
legal terms and DPA; human-acknowledged incident paging; rollout canary and
rollback; and independently signed release authorization.

No production secret, Cloudflare binding, schema migration, Worker deploy,
`main` change, PR #9 merge, customer onboarding, commercial charge or
OpenAI plugin submission is authorized by this feature branch.

Production Connect-to-Axiom general-purpose calculation remains enabled
under its **earlier separate authorization**. Independently unqualified
production methane prediction stays blocked.
