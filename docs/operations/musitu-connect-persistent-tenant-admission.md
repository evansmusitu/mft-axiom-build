# MUSITU Connect — persistent tenant admission research contract

**22 October 2026. Nonproduction code only. No customer accounts created or
new production endpoint enabled.** This extends the 21 October identity
prototype without replacing the separately authorized production Worker.

## Verified offline contract

- Schema: `infra/connect_customer_registry.sql` defines tenants, hashed
  credentials, daily and UTC-minute quotas, and per-request usage events.
- Module: `connect/customer_admission.mjs`, disabled unless
  `CONNECT_CUSTOMER_RUNTIME_ENABLED` is the string `true`.
- Admission: `reserveConnectCustomerRequest({authorization, scope, env,
  nowMs, requestIdFactory})` accepts only the *route-selected* scope. The
  tenant is derived by a database lookup on SHA-256 of the independently
  issued high-entropy `mct_` bearer, never by trusting a request-body tenant.
- The database binding `CONNECT_CUSTOMER_DB` must be available and have
  Cloudflare D1-style `prepare(sql).bind(...args).first()` methods.
- A single `INSERT ... SELECT ... RETURNING` into usage events is guarded by
  SQLite `BEFORE` and `AFTER INSERT` triggers. Within the one SQLite
  statement, a scoped active credential is required, an active tenant is
  required, one request is recorded, and both UTC-day and UTC-minute counters
  are incremented. A daily limit breach returns `CUSTOMER_QUOTA_EXCEEDED`
  (HTTP-equivalent 429); an exceeded minute limit returns
  `CUSTOMER_MINUTE_QUOTA_EXCEEDED` (also 429). Neither publishes a partial
  event/counter write. Each tenant's limits are explicitly configured in
  its registry record; there is no implicit per-customer production default.
  The SQL trigger also rejects `observed_at` values that are not canonical
  UTC timestamps or that disagree with `utc_day`, preventing mislabeled
  accounting events from bypassing either quota.
- `readConnectCustomerUsage({db, principal, utcDay, nowMs})` reads only the
  admitted, server-derived, frozen principal's tenant. Forged principal
  objects are denied, and the credential is checked again against the store
  during reads.
- Usage event keys are `(tenant_id, request_id)`; replay under one tenant
  fails, while other tenants' records remain separate. The request ID must
  be generated by the trusted server using UUID v4. Do **not** pass a
  customer-supplied ID generator into the runtime.
- Invalid credentials, expired/revoked/suspended tenants or credentials,
  missing scope, invalid source clock and missing database fail closed.
  Error responses omit tokens, hashes, SQL text and other tenants' data.
- Quota is a **reservation per admitted attempt**. It is not confirmed
  billable usage or proof that downstream execution succeeded. The refund,
  cancellation and billing policy is unresolved and must be explicitly
  approved before this interface is made public.

## Additional bounded request-body boundary (22 October 2026)

`connect/customer_payload.mjs` is an **offline-only, non-admission**
request reader intended for a future customer-facing Worker, not an import
or execution path of the currently deployed production service. The proposed
research policy is at most **65,536 raw transport bytes (64 KiB)** for one
JSON object. This is a provisional engineering ceiling requiring product
profiling and security sign-off before external customer use.

The reader rejects unsupported HTTP methods and media types, nonidentity
content encoding, nonnumeric/inconsistent `Content-Length`, actual streamed
bytes exceeding the cap (including UTF-8 multibyte text), invalid UTF-8,
malformed JSON and nonobject top-level values. It checks actual byte count
whether or not `Content-Length` is provided and never returns partial
JSON on rejection. Transport errors are sanitized.

The `node --test tests/connect/test_customer_payload.mjs` regression
suite exercised exact-cap success, streamed oversize refusal, declared-size
mismatch, compressed encoding refusal and malformed-data behavior. The
test-first red checkpoint was GitHub Connect CI run `39748095502`:
the disabled implementation failed all 10 new tests while 30 existing
Node tests passed. After implementation, the same expanded Node suite passed
**40/40** in GitHub Connect CI run `39748278360`.

A second offline test surface composes the same transport-reader module
into an isolated Cloudflare **workerd fetch()** handler through
`tests/connect/test_customer_payload_workerd.mjs`. The GitHub run
`39748986714` passed **2/2** workerd HTTP tests (valid JSON and oversized
UTF-8 request) alongside the **13/13** reference SQLite and **2/2**
local D1 tests. Workerd simulation is not a hosted Worker or a real D1
account. No customer-facing routes or authentication settings were changed.

A further adversarial input-integrity round now rejects repeated JSON object
properties at every nesting level, including identical repeated values and
property-name collisions expressed using JSON Unicode escapes. Property names
may legitimately recur in *different* array elements or sibling objects.
The decoder preserves valid string literals that contain JSON-like text.
The scanner has a bounded 128-level traversal limit and fails closed for
unsupported deeper structure.

Regression evidence: Connect CI `39777354968` observed three expected
duplicate-key failures with the old last-key-wins parser (41/44 Node tests
passing); the updated parser passed 44/44 in Connect CI `39777581768`.
The local workerd HTTP suite subsequently passed 4/4 tests in run
`39777752650`, including nested and escaped-key denials. These are
synthetic research-only tests of the request transport boundary, not
evidence of tenant authorization, end-user adoption, or hosted Worker
deployment.

**Not established:** schema-level Mining semantics,
authenticated tenant admission, real D1 metering, clock/CPU limits, global
in-flight request limits, customer billing and security ownership. Future
routing must first authenticate and reserve the request using the trusted
tenant context, then apply the bounded transport reader *and* the already
qualified per-operation semantic validator. A malformed request may still
consume a quota reservation; this must be approved as a product policy.
No new customer API should be deployed merely because these unit tests pass.

## Combined customer-ingress canary — offline research only

`connect/customer_ingress_canary.mjs` is an **isolated callable module**;
it is neither imported by `connect/production_worker.mjs` nor deployed,
routed, exposed to clients or connected to any live Cloudflare secret.

For internal synthetic tests only, it composes **route-selected scope →
tenant credential validation and atomic SQLite quota reservation → 64-KiB
JSON transport and duplicate-key checks**. No Mining planner, Axiom
calculation, forecast, external HTTP request, record storage or commercial
charge is executed. An authorized test request returns only
`NONPRODUCTION_INGRESS_CHECK_ONLY`, `executed:false` and its generated
audit ID. No tenant identity, access token or customer request data is
returned. The independent canary feature flag defaults to disabled.

A denied/unknown credential consumes no quota. **An authorized request with
malformed, duplicate-key or oversized JSON consumes one *attempt*
reservation**, even though no calculation runs. That is a proposed
accounting rule only, not an approved commercial billing policy.

Regression evidence: the disabled seam failed five of six new Node
integration tests as intended in GitHub Connect run `39778665626`. The
composed module and quota-specific test fixture subsequently passed
**50/50** Node tests in run `39779040074` (including all six new
canary tests), with production admission guard preserved. No actual
Cloudflare D1, credentials, staging Worker or real customer was involved.

**Remaining before launch:** a staging-only hosted D1 account with approved
ownership, end-to-end semantic Mining validation and bounded compute,
production-safe tenant-scoped routing and authorization, secure customer
provisioning, reliable revocation, tenancy-wide accounting and data deletion,
real support paging, pilot agreements, performance tests and separate
production release authorization.

## Offline customer quota reconciliation — 25 October 2026

`qualification/audit_connect_customer_registry.py` is a **read-only local
SQLite/D1-compatible accounting reconciliation**, not a hosted D1
qualification or launch. It opens a local database in SQLite
`mode=ro`, enables `query_only`, reads a single transactionally consistent
snapshot, and independently counts admitted-attempt events by tenant/UTC
day and tenant/UTC minute. It compares event-derived counts with the
separate persisted daily and minute quota counter tables, checks that
historical event credentials still reference their original tenant, and
checks timestamp canonicality and scope. Inconsistent counters, orphaned
credential-to-tenant references or malformed events produce
`OFFLINE_ACCOUNTING_INCONSISTENT_NOT_ADMITTED`.

The output contains **only aggregate counts and mismatch totals**; it
cannot contain customer tokens, tenant identities, request IDs, site
details or raw customer request bodies. Missing or invalid SQLite
files fail without producing a success record. The output is
exclusively created and never overwrites another audit. The fixture
runs two fictional tenants, verifies three recorded attempts, and
deliberately corrupts daily and minute counters to prove detection.

Example with an approved disposable, nonproduction SQLite copy:

```bash
python -m qualification.audit_connect_customer_registry \
  --database /private/approved-synthetic.sqlite \
  --output /private/new-accounting-audit.json
```

**Scope limitation:** SQLite snapshot consistency does not prove Cloudflare
hosted D1 cross-region atomicity, customer billing, real credential
issuance, offboarding, operational security, production tenancy or
data-use authorization. Existing general-purpose Connect-to-Axiom
production computation is unchanged. New customer beta admission stays
blocked pending independent staging and human operational evidence.

### Independent local SQLite handles (25 October 2026)

An extra adversarial reference regression opens **two separate on-disk SQLite
connections** to one disposable synthetic two-tenant registry and submits
same-tenant quota reservations through each D1-style binding. A one-attempt
tenant quota must allow only one reservation across both handles; the
second request receives an HTTP-equivalent 429, and both connections must
observe the same one-event/one-minute/one-day counters without cross-tenant
writes. This is a stronger offline transactionality negative control than
calling `Promise.all()` twice on one SQLite handle, but is still **not**
Cloudflare hosted D1 regional concurrency, HTTP load balancing, or production
customer admission.

### Persisted attempt-ID integrity — 25 October 2026

The offline read-only reconciliation now validates that every recorded
attempt contains the server admission contract's lowercase **UUID-v4**
identifier, including its version and variant bits. A malicious or
incorrectly attributed request ID can otherwise leave all daily/minute
counters balanced while breaking the promise that admission allocated the
attempt identifier. Reports emit only the count of malformed IDs, never
any actual token, request or tenant identifier. Corrupted persisted
events return `OFFLINE_ACCOUNTING_INCONSISTENT_NOT_ADMITTED`.
Synthetic adversarial regression tests cover non-UUID text, wrong UUID
version, wrong variant and nonhex characters. This check cannot
authenticate UUID origin or prove billing, customer rights or hosted D1
atomicity. Customer beta admission remains blocked.

### Snapshot quota-limit consistency — 25 October 2026

The offline read-only auditor checks **both** independently reconstructed
usage-event totals and stored daily/minute counters against each tenant's
currently configured per-day and per-minute quota limit in the same SQLite
snapshot. Correctly balanced counters that exceed either limit are now
reported as `daily_quota_limit_exceedances` and/or
`minute_quota_limit_exceedances`, fail
`OFFLINE_ACCOUNTING_CONSISTENT_NOT_ADMITTED`, and never authorize an actual
customer. Tests simulate a formerly allowed usage event followed by a
lowered limit; they prove that equal counters alone cannot satisfy present
policy. These summaries must **not** be interpreted as proof of historic
overcharging or admission misconduct: limits can change legitimately, and
there is no independently verified historical configuration record.
Hosted D1 and production customer beta remain unqualified.

### Defense-in-depth UUID-v4 admission check (offline D1-compatible schema)

The preliminary SQLite/D1 admission trigger now independently rejects
noncanonical request identifiers through explicit position/length/version/variant guards and a short
negative-hex `GLOB`, enforcing lowercase 36-character UUID-v4 formatting. This protects against direct SQL writes that bypass the client-facing
Node module. Failures raise `CUSTOMER_EVENT_REQUEST_ID_INVALID`
**before** quota counters or event history can be modified. Synthetic
local D1-compatible tests cover wrong version, wrong variant, uppercase,
malformed length and nonhex values, and verify zero accounting side effects;
a valid UUID-v4 remains accepted. The change is strictly feature-branch
schema only. It does not migrate a customer database, establish hosted D1
semantics, admit beta customers, or change production workers.

### Local D1 GLOB complexity regression

A full 36-character positional SQLite `GLOB` unexpectedly exceeded the
underlying local Cloudflare D1 engine's complexity threshold, rejecting even
valid server-issued UUIDs. The direct workerd D1 regression now tests
successful canonical insertion **and** invalid direct UUID insertion, and the
trigger uses constant-length field checks plus a short negative-hex GLOB
instead. The SQL-level protection is only accepted when Node SQLite and
local workerd D1 both pass. Remote hosted D1 remains unverified.

### UTC 24:00 boundary rejection (offline SQL/D1)

SQLite accepts the noncanonical `24:00:00.000Z` representation and can
normalize its instant to **the following calendar day**, even if
`strftime` round-trips its original text. That could attribute a
per-minute/day quota to the preceding UTC day. The feature-branch
SQLite/D1 admission trigger now rejects hour `24` explicitly as
`CUSTOMER_EVENT_TIME_INVALID`, without recording a usage event or
incrementing counters. This is test-driven with failing pre-fix Node
SQLite evidence and separately exercised in isolated local Cloudflare
D1. Normal `00`–`23` UTC hour representations continue to work.
Remote D1 remains unqualified and customer admission blocked.
