# MUSITU Mail Fabric v0.2 — isolated durable outbox design and engineering verification

## Implemented

A D1-SQLite-compatible transactional outbox replaces in-process-only mail sending for a separate *pre-production* path (`src/durable/fabric.mjs`). Its only side effects are through an injected D1-style database binding and an injected provider adapter; nothing is automatically deployed. It does **not** create or attach Cloudflare production resources.

Each submission is policy checked, salted/opaque recipient identity is HMAC-committed with a stable operator-held key, payload is AES-256-GCM sealed using a stable externally supplied key and tenant/message AAD, and atomically inserted with a unique `(tenant_id,idempotency_key)`. Concurrent requests with the same key receive the same message identity; a changed request under the key is rejected. Message payload is not returned in public evidence, and cipher data is removed when the outcome finalizes.

Queue workers poll only the configured tenant's own `QUEUED` records and compete through a conditional `UPDATE ... state='QUEUED'` claim. Only the winner may call a provider. A positive provider API response becomes `ACCEPTED_BY_PROVIDER`, negative confirmation `REJECTED_BY_PROVIDER`, and unknown responses `OUTCOME_UNKNOWN`. No state is labelled as inbox delivery. An interrupted `SENDING` lease becomes `OUTCOME_UNKNOWN` after expiration; it is **never blindly retried**, even if the original provider may have accepted it. Lease expiration after a provider side effect is an explicit reconciliation requirement.

Recipient suppressions are keyed as HMACs, persisted across restarts, and checked both before queuing and at dispatch. A suppressed already-queued message transitions to `BLOCKED_BY_POLICY` and never reaches a provider.

The original signed event format is preserved by reconstructing the evidence ledger using explicit, persistent signing and privacy keys supplied by the caller. The default demonstration signing keys are *not* acceptable in production. Proof verification still requires an independently pinned trusted public key.

## Test strategy

`npm test` runs original and added tests. `node --test test/durable.test.mjs` runs SQLite-backed restart, concurrent idempotency, lease-expiry, AES-key mismatch, persistent suppressions and tenant isolation cases. `node --test test/mailpit.test.mjs` validates SMTP DATA, dot-stuffing, rejection and network-disabled guard against a local in-process fake SMTP capture server. Setting `MAILPIT_INTEGRATION=1` additionally sends only to real Mailpit on local SMTP `127.0.0.1:1025` and asserts visibility via its local HTTP API `127.0.0.1:8025`. The CI service is pinned to Mailpit v1.31.4 and is only accessible inside GitHub Actions. No customer mail is sent.

## Strict deployment blockers

This is **not a production launch**. The D1 SQL schema is for an independent dedicated database only; multi-instance D1 transaction/consistency semantics, queue delivery, rate limiting, durable provider event reconciliation, cryptographic key rotation, customer authentication, legal residency, abuse prevention, bounce/complaint ingestion, anti-spam compliance, and independent load/chaos audits are still unverified in real Cloudflare Workers.

The current implementation uses Node `crypto`, Buffer and the native Node SQLite test facade; an actual Workers deployment will require verified `nodejs_compat` compatibility and separate encrypted key provisioning. Local SQLite has different execution characteristics than a live remote D1 binding. The Mailpit adapter is loopback-only, plain SMTP **test infrastructure** and must never become a public relay. Real Mailpit tests require an isolated v1.31.4 Mailpit instance and have no permission to relay externally.

Immediate next engineering candidates: Cloudflare Queue to D1 outbox hints with cron recovery; provider idempotency reconciliation and signed webhook authentication; key custody and public trust anchors; real D1 and Miniflare integration tests; independent security review. No one should claim exactly-once external delivery: failure between provider acceptance and D1 commit remains inherently ambiguous.

Source branch: `product/musitu-mail-fabric-isolated-20261009` only. Protected main, frozen OpenAI, existing MUSITU support Workers, DNS and paying customer records are excluded from this milestone.
