## Why the first attempts failed and how it was resolved

An initial implementation tried to verify the reset through a client stub in the same Queue delivery after a Durable Object called `ctx.abort()`. Cloudflare aborted the session, making same-invocation reads unreliable even though later Queue deliveries could reach the object. Those runs explicitly failed with `NOT_VERIFIED`; none was reported as a successful restore.

The corrected process separates the phases into **two authentic Queue deliveries**:

1. **First delivery:** initialize a unique sacrificial DO with `phase=baseline`, obtain a checkpoint bookmark, update `phase=altered`, request Cloudflare to restore that checkpoint on the next DO session, and abort the DO session. It logs an independently correlatable SHA-256 of the probe ID and a restricted `MUTATED_AND_RESTORE_INITIATED` event, then deliberately requests a Queue retry. It never marks the restore complete here.
2. **Second delivery:** start in a separate Queue invocation and query the same sacrificial object. Return `PASS` only after seeing `phase=baseline`. A response still showing `altered`, invalid resource bindings, a wrong release flag, an incorrectly identified namespace, missing bookmarks or any other uncertainty must fail closed.

The GitHub Action checks **both different-stage events** and the **same unique SHA-256 probe fingerprint**. The two-stage design avoids inferring restoration from just requesting a rollback. The real private staging tenant ledger is not used by this rehearsal.

## Strict limitations

- A sacrificial DO rollback is **not** a complete system disaster-recovery test: the source is synthetic, account remains healthy, network is available and the operation is per-object in-place PITR. No proof exists for actual customer data, account shutdown, data corruption beyond simple mutation, key loss, Cloudflare regional outage, or cross-account migration.
- It does not replace externally held encryption keys, production KMS/HSM custody with recovery testing, immutable offsite encrypted backups, an independent penetration test, or a signed third-party assessment.
- The existing Resend domain was previously confirmed verified, but its account had **no webhooks configured**; real provider delivery event reconciliation remains a production blocker. No real live mail was sent.
- No branch other than `product/musitu-mail-fabric-isolated-20261009` was modified by this work. AXIOM main, support rollout, Claude distribution branch, PR #1 and frozen OpenAI submission remain outside the rollout.

## Outcome

**One production-readiness subtask is now empirically qualified:** real Cloudflare SQLite PITR can restore a known synthetic value within a separately scoped and private object. The entire commercial mail service remains **not production-qualified**.
