# MUSITU Mail Fabric v0.13.0 — Operator safety controls and cloud validation

**Date:** 2026-10-10. **Scope:** isolated `product/musitu-mail-fabric-isolated-20261009` only. **Commercial sending remains disabled.**

## What was implemented

1. **Operator-only manual suppression:** `POST /v1/operator/suppressions`, disabled by default unless `MMF_SUPPRESSION_API_ENABLED=true`. This route requires a separate 32+ character `MMF_OPERATOR_TOKEN`, never the customer's API bearer. The same operator token must not equal the customer token. It works while `MMF_API_ENABLED=false` and `MMF_REAL_SEND_ENABLED=false` so a distressed system can block an address promptly.
2. **Privacy-preserving identity:** each submitted email address is syntactically validated and lowercased, converted using the same persistent HMAC-SHA256 `MMF_PRIVACY_KEY_B64` as `DurableMailFabric`, and only its digest is stored in the existing `mail_suppressions` table. The endpoint returns no raw email address or HMAC digest. Invalid/extra fields and oversize bodies are rejected. No unsuppression endpoint is included.
3. **Atomic operator abuse budget:** `MMF_OPERATOR_DAILY_SUPPRESSION_LIMIT` is a separately configured integer between 1 and 5000, default 200 new suppressions per tenant per UTC day. One atomic SQLite `INSERT OR IGNORE ... SELECT COUNT() < limit` keeps simultaneous requests within budget. Existing duplicate suppressions remain idempotent and do not consume new quota. New requests beyond the cap return HTTP 429 without writing data. Invalid config fails closed before writing.
4. **Emergency sender revocation:** `POST /v1/operator/senders/revoke`, disabled by default unless `MMF_SENDER_REVOKE_API_ENABLED=true`. It requires the same independent strong operator bearer, a JSON body specifying *exactly* the configured sender domain, and `confirm=REVOKE_SENDER`. It invokes the existing tenant-scoped `SenderRegistry.revoke()` and reads back the revoked status. It works even when customer outbound operations are disabled. Different tenants' sender ownership is unchanged.
5. **Private stage operator qualification:** `MMF_STAGE_OPERATOR_SUPPRESSION_PROBE` runs only inside the already isolated Cloudflare Queue-to-SQLite Durable Object Worker. It reuses the production operator HTTP handler internally with deterministic synthetic test addresses, refuses the ordinary customer token, persists a keyed suppression, proves duplicate idempotency and confirms that a later outgoing synthetic message is blocked. No public route or real provider network call is enabled.

## Operational configuration

Use a dedicated operator key, separate from customer API credentials. Set `MMF_SUPPRESSION_API_ENABLED` and `MMF_SENDER_REVOKE_API_ENABLED` to `true` only after appropriate API authentication, production security review and networking safeguards. Do **not** add those flags to the existing synthetic Cloudflare Worker deployment. The real stage Worker stays non-public, has no outbound mail and exposes only its private Queue consumer.

Never log operator tokens, raw recipients, signing keys or customer HMAC keys. Persist and back up the original 32+ byte tenant privacy key through a genuine managed custody process; losing or replacing it will prevent existing suppressions from matching new recipient submissions. The pre-existing encrypted offline backup includes `mail_suppressions`, but recoverable offsite production backup custody is still unqualified.

## Limitations and remaining genuine blockers

- There is **no current proof of a real Resend-delivered event** into MUSITU. The connected Resend account previously returned **zero configured webhooks**. Synthetic Svix signatures validate code logic but are not actual provider-origin events.
- The private stage Worker cannot receive external webhooks. A separate explicitly approved public ingress and correctly registered authenticated provider webhook remain necessary before customer delivery.
- Disposable Cloudflare staging keys are not customer-owned KMS/HSM-backed production key custody, and no independently held root/signing key or full cross-account cloud restore certification exists.
- Sender revocation uses the existing domain ownership registry; it prevents future sends subject to live checks, but cannot recall mail already accepted by a provider. Manually suppressing a recipient similarly does not reverse an already in-flight network attempt.
- Legal consent, data-residency, regional retention/deletion rules, contractual obligations, financial reconciliation, billing, monitoring and independent assessor's signed report are not yet qualified.
- Protected AXIOM main, support production, Claude distribution, PR #1 and the frozen OpenAI review surface were not modified.

**Result:** additional safeguards are implemented and have explicit, inspectable software/cloud evidence. Commercial production release is **not authorized or claimed**.
