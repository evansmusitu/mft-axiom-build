# MUSITU Mail Fabric v0.14.0 — Separated webhook-only ingress and real private Worker provisioning

**Date:** 2026-10-10. **Product branch:** `product/musitu-mail-fabric-isolated-20261009`. **No customer sends or public routes enabled.**

## Architecture and security gates

The new `src/edge/webhook-only.mjs` is a dedicated Cloudflare Worker entrypoint with exactly one possible HTTP handler: `POST /v1/webhooks/resend`. It refuses all customer message APIs, sender ownership commands, operator suppressions/revocations, diagnostics and general health endpoints with 404. It refuses processing with 503 unless `MMF_API_ENABLED=false`, `MMF_REAL_SEND_ENABLED=false` and `MMF_WEBHOOK_ENABLED=true`. When explicitly activated later, it delegates only authenticated, recipient-bound, idempotent Svix/Resend webhook processing to the existing durable fabric; it has no provider send capability.

The config `wrangler.mmf.webhook-only.template.jsonc` is fail-closed: `workers_dev=false`, `routes=[]`, **all six public/customer/provider/operator feature flags are false**, no embedded credentials, and a new `MMF_RECEIPTS` SQLite Durable Object namespace separate from the existing `MMF_LEDGER` staging namespace.

The new resource created in the Cloudflare account is **`musitu-mail-fabric-webhook-isolated-20261010`**, not the AXIOM runtime, support-production Worker or existing MUSITU Mail Fabric staging Worker. The class `MmfStagingSqliteDO` is reused as internal private SQL RPC code, but it is deployed to a separate namespace and has an independent datastore.

## Release gates still closed

- The connected Resend account was read-only inspected on 2026-10-10 and reported **zero configured webhooks**. Real Resend-issued event delivery to the MUSITU ingress is therefore **not tested or verified**.
- No public DNS entry, `workers.dev` endpoint, custom domain, preview URL or public route is activated. A real Resend webhook requires an explicitly approved secure public endpoint, proper domain scoping and independent verification that existing support operations cannot be affected.
- No `MMF_WEBHOOK_SECRET`, message encryption or signing keys, `MMF_STORAGE_RPC_SECRET`, tenant configuration, KMS/HSM keys or real customer data were provisioned into the new Worker. Every sensitive feature stays **off** until authorized independent secrets, sender ownership, provider registration and testing exist.
- An external assessor's signed security report, cross-account encrypted backup custody, actual genuine outage recovery, financial/abuse operating model and relevant consent/data-residency review are still missing.
- No real external mail was sent or provider event received. A local self-signed Svix event is **not** external delivery evidence.
- AXIOM main, support production, Claude distribution, protected PR #1 and the frozen OpenAI review remain outside the changes.

## What is prepared for the next authorized verification

The isolated webhook Worker and database now exist but are disabled. A subsequent independent provider-qualification workflow can, when explicitly authorized, configure **separate** secrets, register an appropriate isolated Resend webhook against a dedicated approved ingress, obtain a real provider-origin test event, verify its Svix signature and recipient correlation, observe durable storage and suppression, and then safely disable the endpoint. Such a workflow must not reuse AXIOM's support webhook subscription or assert inbox delivery from provider acceptance alone.

**Current status:** v0.14.0 implementation and private cloud provisioning proven; customer commercial release is still **BLOCKED**.
