# MUSITU Mail Fabric v0.4 — Durable abuse prevention and verified feedback

**Status:** isolated pre-production implementation. No paid resources, no DNS changes, no customer deployment.

## Goals

1. Prevent a configured tenant from submitting more than its UTC-day transactional message allowance, including parallel writers.
2. Preserve idempotency even after quota exhaustion.
3. Automatically and durably suppress a known recipient on an authenticated `email.bounced` or `email.complained` Resend event.
4. Continue ingesting legitimate provider events when outbound mail is paused.
5. Signal transient backend failure with a retryable 503 rather than a misleading terminal 400.

## Technical design

The `mail_messages` table gains a required `recipient_hmac` column. This key-derived opaque identifier is created during enqueue, before the cleartext envelope is encrypted; after send, the encrypted envelope is purged, but the recipient HMAC supports bounce/complaint suppression without storing a raw address. `privacyKey` must remain a stable tenant-specific, secured secret across Worker restarts. Rotation requires a separately engineered key-transition procedure.

The UTC-day quota uses an atomic `INSERT OR IGNORE INTO mail_messages ... SELECT ... WHERE COUNT(...) < configuredLimit` statement. Every accepted/new transaction consumes one unit for its initial UTC day, regardless of later provider outcome. Safe idempotent repeats of an existing key return the stored row and do not consume another unit. A changed message with the same key is rejected. The Worker takes the cap from `MMF_DAILY_SEND_LIMIT` (default 100); client-supplied limit fields have no effect. Quota exhaustion maps to 429, other policy rejections to 422.

Authenticated Resend/Svix signatures, timestamp acceptance and event ID de-duplication are mandatory. Only a matching previously accepted `provider_id` in the configured tenant can trigger a durable keyed suppression. The event is inserted first, then suppression; if the suppression write fails and the provider replays the same signed event ID, the duplicate path replays suppression safely. Distinct payloads sharing an event ID remain conflicting. Already queued sends independently check durable suppression at dispatch time. All email-delivery statuses remain provider assertions, not proof of inbox placement.

The Worker uses a restricted receipt-only provider inside authenticated webhook handling when outbound sending is disabled. That adapter cannot dispatch network requests; the ordinary queue and scheduler still fail closed when real sending is disabled. Auth failure gives 401, malformed event 400, conflicting event ID 409, temporary backend processing failures 503.

## TDD record

`node --test test/production-safety.test.mjs` initially failed all five targeted cases before the quota and suppression implementation (missing rejection assertions). After implementing quota and suppression, all five passed. New Worker quota and paused-feedback tests failed with expected status mismatches (422 vs 429, and 400 vs 202), then passed after targeted changes. Transient backend failure case initially returned 400 rather than 503, and passed following the response fix. An additional regression demonstrated historical idempotent receipt lookup initially failed after suppression, and was corrected to prioritize unchanged existing idempotency keys before evaluating the suppression status for new sends. No previous assertions were weakened to manufacture a pass.

## Honest rollout boundaries

No public sending service, provider key, operational SLA or independently certified legal proof is delivered by this change. Production still requires sender-domain ownership verification, persistent key registry and rotation, API request rate limits and anti-spam scoring, delivery reputation evaluation, external customer authorization, consent and retention policies, monitored dead-letter queues, independent load/chaos trials, and finance/abuse operations. A real D1/Queues deployment must use **new isolated Cloudflare resources** and separate explicit authorization; never share the AXIOM production database, tokens or Workers.
