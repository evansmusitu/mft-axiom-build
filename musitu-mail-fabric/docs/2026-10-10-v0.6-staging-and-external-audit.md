## Cloudflare staging gate

One-shot workflow `.github/workflows/mmf-staging-resources-20261010.yml` uses existing scoped credentials stored in `axiom-support-production` solely to create two separately named and owned **staging resources within the same Cloudflare account**: D1 `musitu-mail-fabric-staging-20261010` and Queue `musitu-mail-fabric-staging-20261010`. It does **not** deploy, route, expose, or attach a live Worker; does not alter DNS, billing, support databases, OAuth, production code, or existing queues. Existing same-name resources are reused after exact metadata verification. Failing provider access stops immediately; no fallback to broad global API keys.

The D1 schema is applied only to that D1 UUID. Four expected tables are verified by live readback. No actual customer data, provider email, webhook, key pair, or real queue message is sent. Cloudflare production failover and genuine network-outage behavior remain **unproven** until a separately isolated Worker and synthetic remote queue consumer pass durable failure recovery tests. Successful resource provisioning **alone is not** distributed recovery testing.

The workflow is guarded against other branches and historical replay. The account and staging resource names are exact allowlisted constants, and its provider credentials are not printed.

## Actual security status

Sender-owned DNS TXT challenge is represented by the tenant-scoped `SenderRegistry`, with cryptographic challenges, short expiry, explicit revocation and fail-closed DNS timeouts. This currently proves DNS control **when** verified, not legal identity, delivery-domain DKIM/SPF configuration or continued control beyond TTL.

The existing D1 outbox tracks `ACCEPTED_BY_PROVIDER` distinct from `DELIVERED_REPORTED` and from human receipt. Signed webhooks, complaint/bounce suppression and replay checks are exercised using deterministic test fixtures. Real authenticated Resend/Postal webhooks from a controlled test account are **not** yet observed in a live receiving service.

Worker signing secrets and encryption keys must be created/stored in a dedicated secrets-management system for the eventual isolated staging Worker. Current local test private keys do not qualify as managed custody; an HSM or Cloud KMS is not present. A secret must never be printed, committed, or sent to ChatGPT.

## Independent external audit request (not yet commissioned)

A third-party assessor, independent of the implementer, must receive the source commit, reproducible tests, evidence format, and anonymized stage logs and review:

1. Cross-tenant access and role escalation, sender domain proof and delegated AI-agent authorization.
2. API abuse, phishing/spam controls, per-tenant and per-recipient quotas, bounce/complaint feedback loops.
3. Crash-consistency and atomicity: retrying queue messages, duplicate requests, lease expiry, provider API uncertainty, remote outage and partial commits.
4. Event verification: forged signatures, replay ID collisions, out-of-order provider claims, loss of provider identity, suppression repair.
5. Key custody: independent root pinning, historical issuance epochs, rotation, revocation, secret recovery and public attestations.
6. Privacy: encrypted storage, lawful data residency, deletion, retention, log redaction and regulated-sector obligations.
7. Deployment integrity, worker visibility, minimal token scope, dependency integrity and reproducible artifact hashes.

**Acceptance requires a signed report**, named assessor, dated scope and finding severities, zero open critical or high findings, and remediation/regression evidence. Self-authored tests and internal review are valuable but do not count as independent evaluation.

## Hard production gates

No public customer email until independently verified domain identity and authorized delivery provider; successful real delivery-event round trip; managed key custody and rotation; remote staging D1+Queue+Worker tests; validated rate limits, abuse procedures, backups and recovery; independent security report; legal/privacy and operator review. Provider API accepted does not mean inbox delivered. Do not claim enterprise SLA, compliance certification or global-first status without external evidence.
