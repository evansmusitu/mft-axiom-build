Date: 2026-10-10 (UTC). This document describes a **non-public, synthetic-only** Cloudflare staging exercise, not customer production or an independent security certification.

## Actual cloud infrastructure

- Isolated Cloudflare Worker: `musitu-mail-fabric-staging-20261010`, with `workers_dev: false`, zero configured public routes, and public preview disabled.
- Isolated Queue: `musitu-mail-fabric-staging-20261010`, id `1ff13f921b90488397e7f76970117aee`.
- Isolated SQLite-backed Durable Object class: `MmfStagingSqliteDO`. It is not an AXIOM database, and no new D1 database was created.
- Network email, public API and external webhook flags are explicitly disabled. Every submitted test message is a random synthetic `MMF_STAGE_PROBE` or `MMF_STAGE_RETRY_PROBE`, never a real customer message.

## Boundaries of the evidence

- The test explicitly **injected a bounded queue retry** inside real Cloudflare infrastructure. It is **not** evidence of surviving a naturally occurring Cloudflare network outage, a regional outage, lost durable storage, provider SMTP failure or control-plane incident.
- Storage write and readback were observed through the private Worker logs and its own Durable Object RPC. Third-party tamper-resistant external storage attestation has **not** been established.
- Staging keys are disposable Cloudflare secrets. They do not provide HSM/KMS-backed custody, user-owned root keys, guaranteed recovery after key loss, attested key rotation or historical certification.
- The new proof is not real Resend/Postal webhook reconciliation. All delivery-provider integrations remain disabled for customer sending. No real external deliverability percentages or cost claims can be made.
- An independent third-party security assessment has **not** been commissioned or completed. Internal CI and self-authored failure tests must never be described as independent audits.

## Remaining production-blocking qualifications

1. Independently controlled long-lived encryption/signing key custody, verified backup/restore, trustworthy public key anchors and revocation.
2. Authorized end-to-end provider sending with authenticated actual delivery, bounce and complaint webhooks, including provider-side correlation and human-approved recipients.
3. Safe outages and recovery exercises in separately provisioned sacrificial resources; no intentional disruption of AXIOM or this shared account's other services.
4. Rate limits, anti-abuse review, legal consent/retention/data-residency controls and real operational monitoring at customer-scale.
5. External assessor's signed report with named scope and independent critical/high remediation closure.
6. Approved public DNS domain, financial/operations model and a contractual production gate.
