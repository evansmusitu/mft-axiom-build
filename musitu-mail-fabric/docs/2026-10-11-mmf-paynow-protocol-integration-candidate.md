# MUSITU Mail Fabric — Paynow protocol + authority candidate (isolated)

**Date:** 2026-10-11. **Status:** OFFLINE CANDIDATE ONLY; explicitly **NOT a live Paynow product, qualified settlement, permission to invoice, or production release**.

## What was grounded externally

- Official Paynow API: https://developers.paynow.co.zw/docs/paynow/initiate_transaction/ — private `POST /interface/initiatetransaction`, URL-encoded `id`, `reference`, `amount`, `returnurl`, `resulturl`, `status=Message`, SHA-512 hash. Never call the provider from the browser.
- Official Paynow hash: https://developers.paynow.co.zw/docs/paynow/generating_hash/ — concatenation of decoded field values in transmitted order excluding `hash`, append server-held merchant integration key, uppercase SHA-512. The test asserts the **full documented 128-digit sample vector**.
- Official status: https://developers.paynow.co.zw/docs/paynow/status_update/ — Paid is provider payment accepted pending bank settlement; Awaiting Delivery and Delivered are suspense/provisional, Created/Sent unpaid, Cancelled/Disputed/Refunded distinct. This candidate NEVER treats Disputed as a successful refund or charges. Paynow recommends independent poll on important callbacks.
- Official poll: https://developers.paynow.co.zw/docs/paynow/polling_status/ — HTTP POST with empty body to the *signed and allowlisted* `/Interface/CheckPayment/?guid=...` Paynow URL.
- Cloudflare service binding: https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/http/ — future MMF-specific private Worker may call the existing private payment authority Worker via an explicit service binding. Binding alone does not create missing product routes or grants.

## Candidate code present and qualified offline

- `src/commercial/paynow-native-protocol.mjs` strictly validates URL-encoded provider status messages, forbids duplicate parameters and unsafe credentials, validates official status and exact provider-reference and MMF order identity, constant-time verifies SHA-512 signatures, and validates allowlisted poll URL. A WeakSet marks verified in-process provider event objects; JSON/forged records cannot impersonate parsed verified evidence. Returns **no entitlement**, no bank-settlement proof and never initiates provider access. Future Paynow status fields allowed in this limited contract require separate provider qualification before activation.
- Its server-side `buildMmfPaynowInitiateRequest()` builds only the fixed unapproved $99 USD MMF preparation-SKU request, exact original MUSITU Paynow integration identity and fixed `https://payments.mftintelligence.com/mmf/return/{order}` and `/mmf/result/{order}` destinations. These MMF endpoints **DO NOT EXIST LIVE**; the builder does not send the request. The API key is only a parameter to isolated authority code and MUST remain stored only in the existing shared authority in any approved future deployment.
- `src/commercial/paynow-private-authority-candidate.mjs` accepts authenticated callback form, checks MMF order/price/tenant, **performs one independent allowlisted Paynow status poll via injected transport**, bounds response to 4 KiB, verifies second provider SHA-512 signature and cross-matches order, payment reference and amount, then emits an Ed25519 authority-signed MMF-only paid or refunded receipt. The signer must be an actual *authority-managed* private key, not an ephemeral fixture. A callback alone can NEVER mint a receipt. A "Disputed" status never becomes a "refunded" receipt. `Paid` is not bank settlement or invoice authority.
- `test/paynow-native-ledger-e2e.test.mjs` connects an **emulated** real-format Paynow callback, emulated status poll, ephemeral Ed25519 signer, genuine SQLite in-memory MMF order database and staged `PENDING → PAID_SANDBOX → REVERSED_SANDBOX` transition. Replay is idempotent and cannot revive a reversed order. No customer data, charges, refunds or email sends take place.

## 2026-10-11: current Paynow optional-metadata compatibility and fraud-release hardening

Paynow's current status-response documentation also permits optional `paymentinstrument`, `paymentinstrumentname`, `paymentinstrumentnationality` and `paymentchanneleci`, in addition to the previously supported payment-channel and fraud fields. The local strict SHA-512 parser now admits these **only inside an authenticated response**, validates the entire original field order, and discards these fields before constructing product-facing receipts or admissions. Sensitive payment-instrument/cardholder strings must never be written to the MMF ledger, receipts or audit logs. Tokenized payment `token` and `tokenexpiry` remain **unsupported and rejected**; MMF does not request card tokenization or recurring payment instrument collection.

A valid `Paid` provider status accompanied by an explicit adverse/unknown `paymentfrauddecision` is **not a paid authorization**. Only a missing decision or the documented `Issue` decision is allowed for a `Paid` response. Signed `Reject`, `Request Manual Review`, and unknown decision values fail closed, whether present on the callback or the independently polled status. Negative tests specifically observe no provider poll for rejected callbacks and no paid claim issuance for a rejected poll. This deliberately conservative policy still requires live merchant review before any production activation.

These tests are run with fake merchant keys and an injected provider transport. They do **not** establish that live Paynow has approved MMF, prove an actual charged transaction, or satisfy the MMF release gates.
