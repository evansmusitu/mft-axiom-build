# MMF Paynow — isolated Cloudflare deny-all canary, owner-authorized

**Date:** 2026-10-12. **Scope:** new dedicated worker `mmf-paynow-isolated-deny-canary-20261012` only. This is not a shared Paynow deployment, merchant integration, payment pilot, customer mail release, or production activation. Owner authorization permits this low-privilege isolated infrastructure check; it cannot substitute for the independent production release signature required for changes to existing shared Workers.

The canary source (`src/staging/mmf-paynow-canary.mjs`) rejects **every** request with HTTP 503, never reads environment secrets, does not initiate outbound requests, has no service/database bindings and is never associated with a route or DNS record by this workflow. Workers.dev and preview URLs are both explicitly disabled and read back. The installer (`src/staging/deploy-mmf-isolated-paynow-canary.mjs`) pins exact account, branch and script hash, verifies both legacy payment Worker names appear in the account's script list without reading their source, refuses to overwrite a preexisting canary, uploads the new canary only, disables its subdomains, and reads back source/settings. It attempts cleanup of **only the newly created canary** if post-install checks fail. It cannot alter either shared payment Worker; all sensitive credentials stay in the existing GitHub Actions encrypted environment. No merchant credential or third-party Paynow API request is in the code.

The GitHub workflow is restricted to `product/musitu-mail-fabric-isolated-20261009` and runs the seven focused deny-all tests, full syntax and regression suites, and mandatory blocked commercial gate prior to the isolated Cloudflare operation. The workflow uses the existing `axiom-support-production` environment exclusively as a transport for the stored Cloudflare API token. If that token lacks Workers Scripts Write permissions, the deployment **fails without modifying a shared Worker**. Do not interpret an unsuccessful deployment as a successful canary.

The source is deliberately non-financial and does not implement the missing MMF route-specific merchant features. The separate MMF Paynow routes and dedicated secret references remain absent from existing production Workers until a qualified change is independently reviewed and approved. Owner authorization does not create merchant product rights, grant dual approval, satisfy nonexportable-secret-safe rollback, or authorize a real payer transaction.

After any successful canary: record the exact GitHub run SHA, Cloudflare script readback, subdomain disabled state and zero bindings as evidence. Keep commercial activation false and complete merchant eligibility, independent approval, secure dedicated secret provisioning and the legacy-product rollback/canary programme before even considering changes to shared Workers. On a failed run, inspect sanitized logs and Cloudflare read-only script inventory without guessing success.
