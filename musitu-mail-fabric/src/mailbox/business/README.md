# MFT Intelligence Mail — business mailbox pilot
Scope: single authorized business mailbox, no Google/Gmail dependency. The old sibling preview remains local/synthetic only. Production MMF routes, flags, and DNS are not modified.
## Local qualification
From this folder use Node 22+, install reviewed dependencies with npm install, inspect the lockfile and run npm test and npm run check. Use a fresh D1 database and R2 bucket; apply schema.sql only to that database. The template intentionally lacks IDs, secrets, Access issuer/audience and a route. Never deploy it unchanged. The pilot requires a real provider test, independent browser/session checks and recovery verification before release.
## Cloudflare pilot configuration
1. Read all existing Email Routing rules and destinations. Do not change the MX records, existing support routes or catch-all. Confirm mail-pilot@mftintelligence.com is unused. Reserve only that address, after deploying and testing the isolated Worker. Do not use Wrangler-managed routing to overwrite current rules.
2. Create a dedicated D1 and private R2 binding (MMF_DB and MMF_RAW) with retention, restricted access and recovery plan. Bind only the dedicated resources. Supply MMF_OWNER_EMAIL, MMF_ACCESS_ISSUER and MMF_ACCESS_AUD from a dedicated Cloudflare Access application for https://mail-pilot.mftintelligence.com with an exact owner allowlist and MFA. Keep workers.dev and preview URLs disabled; custom hostname must have Access before exposure. Verify unauthenticated requests fail and signed claims for another user fail. Confirm logout invalidates access; this code uses Access assertion validation, not a standalone session system.
3. Confirm provider terms and use a scoped Resend key stored as Worker secret RESEND_API_KEY. Do not commit or print it. Leave send/receive off until qualification. Enable receive only for unused pilot route; send only for deliberate controlled business correspondence within approved provider policy and quotas. Check provider logs for pending or unknown outcomes; never automatically retry them. A provider acceptance is not proof of delivery.
4. Test inbound from a controlled external account, read/search/archive/restore in UI, save draft and verify across reload, send a reply to that controlled account and verify receipt. Test oversized input, MIME/HTML, unauthorized requests, duplicate inbound, repeated send, storage failures and logout. No production mail migration until evidence passes.
5. Before existing-address migration, verify exact old forwarding destination, authorization and retention. Existing addresses require explicit route approval and a separately verified forwarding destination in code. Test forwarding continuity and rollback; leave all current mail routes untouched if any test fails.
Limitations: plaintext body only in UI; raw MIME retained privately, no attachment download or HTML rendering, 50 results per folder, no independent multi-user provisioning, no verified MFA/session revocation yet, no production deploy, no send/receive proof. Raw MIME and plaintext metadata stored in dedicated cloud resources; app-level encryption and retention automation are not implemented. Never use this pilot for confidential real business mail until storage/security review and data handling approval.
