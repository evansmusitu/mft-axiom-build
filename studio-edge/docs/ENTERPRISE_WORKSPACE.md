# MUSITU Intelligence — opt-in enterprise tenant workspace foundation

This feature is **NOT LIVE** and has no configured Cloudflare Access identity or D1 binding in existing production or canary Wrangler configurations. It does not turn the five local encrypted browser slots into cloud accounts.

## Security boundary
- URL: GET/PUT/DELETE /api/enterprise/tenants/{tenant_id}/artifacts?id={artifact_id}
- Auth: signed RS256 JWT in cf-access-jwt-assertion, validated against the configured Cloudflare Access issuer's public JWKS, exact issuer, audience, expiry, issued-at and signature.
- Authorization: on EVERY request, the signed subject must have an ACTIVE row in D1 tenant_memberships for the URL's tenant; owner/editor can write, viewer can only read. The client never sets its authorization role.
- Storage: server receives a strictly shaped opaque AES-GCM envelope (version=1, 12-byte base64url IV, base64url ciphertext including authentication tag). Server does NOT encrypt, decrypt, manage keys, validate an encryption password, or verify the plaintext. Clients must use genuine authenticated encryption with random unique IVs.
- Durable tenant-scoped rows use compound (tenant_id,artifact_id) keys. Mutation and minimal audit event are written in one D1 database transaction. The SQL statement itself checks active membership and owner/editor role, closing revoked-access races between an earlier JS lookup and database mutation; the read query joins active membership as well. Audit events are inserted only when SQLite reports a changed row. A missing DELETE returns 404 without a false audit. Delete removes ciphertext, but retains audit rows without content.
- **Concurrent editor safety: required strong ETags**. GET returns `ETag: "<uuid>"`. To create, send PUT with `If-None-Match: *`; to replace, send PUT with `If-Match: "<etag-from-last-read>"`; DELETE also requires `If-Match`. Every successful PUT rotates the revision UUID in the same SQLite statement as ciphertext mutation, so stale clients cannot silently replace or delete newer work. Mutations lacking preconditions return HTTP 428; malformed or weak tags return 400; version conflicts return 412 without ciphertext or audit mutations. Changed membership at SQL execution returns 404 instead, without exposing content. ETag is a concurrency token, **not** authorization or an encryption key. This does not implement automatic multi-device synchronization, account sessions, or offline conflict resolution.
- A **new 50-artifact per-tenant row cap** is enforced by the `0002` SQLite AFTER INSERT trigger. The same tenant can update existing records at capacity and reuse freed slots after deletion. A recognized quota abort maps to HTTP 409 `TENANT_ARTIFACT_LIMIT`. A separate `0004` SQLite trigger enforces up to **20 successful mutations per tenant in any rolling 60-second window**, before adding an audit row. Mutation and audit are committed or rejected together, and excess returns HTTP 429 `TENANT_MUTATION_LIMIT`. This is NOT a global GET/authentication/network/AI quota. This bounds *stored artifact count in the dedicated D1 database*, NOT request frequency, aggregate audit growth, AI consumption, bandwidth, worldwide cross-provider costs, or any already-deployed service. It remains inactive until the new D1 database and migration are actually provisioned and independently verified.
- No cross-origin browser access beyond the MUSITU website; browser Origin is NOT authentication. GET with `?id=<artifact_id>` reads an encrypted item; GET with no `id` now lists only bounded **metadata** (artifact identifier, revision, update time) using a maximum 10-item ordered keyset page. Optional `?after=<artifact_id>&limit=1..10` pagination is constrained and rejects mixed/duplicate query parameters. Tenant membership is checked inside the list query, and the listing never returns ciphertext or cross-tenant items. No provisioning API is exposed.
- This feature is only a foundation, NOT a production-qualified enterprise workspace. Rate caps, operational deletion policy, customer consent, backups, abuse monitoring, identity lifecycle, verified revocation latency, session control, transport and threat-model acceptance remain gating work.

## Deployment prerequisites (separate authorized resources)
1. Provision an isolated dedicated Cloudflare D1 instance, **not** any existing Neon/customer/project database; apply `migrations/0001_enterprise_workspace.sql`, `migrations/0002_enterprise_tenant_artifact_limit.sql`, and `migrations/0003_enterprise_artifact_revision.sql`, and `migrations/0004_enterprise_mutation_budget.sql` in that order there. Do not point either migration at unrelated/customer databases.
2. Provision and verify Cloudflare Access protected identity application, and configure WORKSPACE_DB binding, ACCESS_TEAM_DOMAIN (https://<team>.cloudflareaccess.com), ACCESS_AUDIENCE (actual application audience). Do not log or echo tokens.
3. Insert tenants and memberships through a separately audited administrator path, not from user-supplied tenant claims.
4. Deploy first to a NEW private canary, not the public Worker, and run valid/invalid JWT including oversized upstream JWKS, metadata pagination/revocation, tenant A/B, 20/21 mutation-rate limits, concurrent revocation, 50/51-item quota, optimistic concurrent editors (create-only, update-only, stale updates, stale deletes, replay after deletion), real D1 encrypted save/read/delete and independent security/privacy acceptance.
5. No production promotion without reviewed rollback, controls, cost and retention approval.

Existing Wrangler files intentionally do not reference WORKSPACE_DB or Access variables. Without complete configuration every enterprise API request returns NOT_CONFIGURED; ordinary public AI endpoints stay unchanged.

## Additional security verification (not production)
- Adversarial tests reproduce the 21st audit mutation succeeding before the `0004` migration, then prove the database rejects it without partial ciphertext or audit writes. This is database-global only for that tenant and does not cover unsigned GET probes or aggregate model spend.
- Tests prove keyset listing pages never contain ciphertext or another tenant's metadata, and reject malformed or duplicate pagination parameters.

## Disabled browser integration building blocks (not deployed)
- `client-encrypted-artifact.mjs` implements AES-256-GCM for a **caller-supplied, non-extractable compatible CryptoKey**. It generates a fresh random 96-bit nonce on each encryption and authenticates the tenant and immutable artifact ID in AES-GCM additional authenticated data. Maximum UTF-8 plaintext is 8,000 bytes; server receives only `{version,iv,ciphertext}`. The caller must independently own key derivation, secure key recovery, and session lifetime; the server cannot recover lost encryption keys.
- `enterprise-client.mjs` is a manual, opt-in SDK. Its endpoint validation limits it to approved HTTPS Worker hosts under this Cloudflare account; caller injects a short-lived signed Access JWT provider and fetch implementation. It explicitly excludes browser cookies, automatic background calls, silent conflict retries, token persistence and local slot migration. GET decrypts only with the caller's key; create requires `If-None-Match: *`, and replace/delete require an explicit ETag. It reports 412 rather than losing a concurrent edit.
- These files are **not imported by the current public website or deployed Worker**. They are not a sign-in experience and do not make encrypted browser-local slots into durable cloud accounts.
- **Never auto-convert or upload the existing five local AES-GCM/PBKDF2 slots.** Their encrypted file format and key derivation are separate. Any future opt-in conversion must first decrypt explicitly on-device with a user-entered passphrase, require affirmative upload consent, fit the new 8 KiB plaintext limit, and leave original local ciphertext untouched.
- Positive/adversarial tests verify tenant-bound AAD, random IVs, tampering failures, Unicode round trips, browser JWT headers, no cookie credentials, invalid host rejection, bounded metadata pagination and no retry on stale ETags.

It does **not** write to disk, transmit a backup to third parties, change local slots, decrypt into the exported object, or initiate restoration. The client first compares per-item revisions, then runs a second, bounded complete metadata inventory to reject changed, removed, or newly inserted items observed before completion. ## Oct 25 additional recovery and privacy controls (development only)
- `inspectEncryptedBundle(bundle)` verifies the full same-tenant encrypted export **offline**, authenticating every AES-GCM envelope under its bound tenant and document ID. It returns only `{tenantId,count,ids}`, never plaintext, credentials or encryption keys. Malformed/duplicate/out-of-order and unrecognized bundles are rejected before JWT acquisition or network calls.
- `restoreEncryptedArtifact({bundle,id,acknowledgeCreateOnly:true})` is deliberately **one document at a time**. The caller must affirm the operation explicitly, pick an ID from the authenticated backup, and provide the original compatible non-extractable key. It sends ciphertext only with `If-None-Match: *`; conflicting existing records stop with HTTP 412. It never silently overwrites, migrates five local slots, transfers between tenants, auto-retries or imports a batch. The ciphertext bytes are snapshotted before asynchronous token acquisition to prevent post-verification mutation.
- The client now validates complete server mutation acknowledgments and rejects false `200 OK` writes, deletes, stale ETags, malformed metadata revisions, misordered IDs and corrupt cursor chains. Real SQLite integration tests exercise restoration, wrong tenant/key rejection and no plaintext in the Worker/database.
- `enterprise-audit-retention.mjs` is an **unwired, operator-invoked, manual-only** helper. It defaults to dry-run/inert and requires explicit `execute:true`; when authorized it deletes at most 100 expired audit metadata rows **only for the explicitly selected tenant ID** per call, using a proposed default 30-day period. Global/unscoped deletion requests fail closed. It never reads/deletes ciphertext and has no HTTP/cron/cloud bindings. The legal retention policy, DSAR/erasure process and operator approval remain **NOT accepted**.
- See [ENTERPRISE_PRIVACY_OPERATIONS.md](ENTERPRISE_PRIVACY_OPERATIONS.md). All additional mechanisms are offline/CI verified only; there is no Access/D1 production or private-canary sign-in.

## Additional controls — Oct 25 isolated continuation

- The development-only enterprise handler **fails closed without both** dedicated `WORKSPACE_AUTH_RATE` and `WORKSPACE_READ_RATE` Cloudflare rate-limit bindings. Every non-OPTIONS enterprise call consumes an **authentication probe** event *before* contacting the Access JWKS endpoint; denial returns 429 `AUTH_RATE_LIMIT`. Every successfully authenticated GET, including catalog pages, consumes a separate `WORKSPACE_READ_RATE` event **before any tenant D1 lookup**, keyed by a shortened SHA-256 pseudonym of tenant and signed Access subject; denial returns 429 `READ_RATE_LIMIT`. Missing/failing controls return 503 `RATE_CONTROL_UNAVAILABLE`, without fetching signing keys or reading tenant data.
- These are additional **per-binding, potentially Cloudflare-location-local** safeguards, NOT hard worldwide request/cost caps. Shared authentication-probe buckets can also impact innocent callers under abuse. Provision and test concrete thresholds, binding scope, expected load and costs **only on an independently authorized, isolated private canary**. Existing production and capacity-canary Wrangler files intentionally have none of the new bindings and remain unchanged.
- The isolated `enterprise-tenant-erasure.mjs` maintenance helper requires specific independently verified tenant IDs, a nonsecret authorization reference, explicit legal-hold-clearance assertion, exact typed confirmation, and `execute:true`. Its default dry run issues no D1 queries. The approved test harness uses D1-style atomic transactions to remove only the selected tenant's audit rows and tenant record (cascading associated tenant memberships and opaque ciphertext), with cross-tenant and rollback tests. This does **not** remove Cloudflare backups, local vault slots, exported bundles or third-party copies and is **not** wired to the Worker, schedulers or customers. Real deletion requires independent legal, owner and privacy authorization.

## Offline passphrase-derived key descriptor (NOT IN PUBLIC PRODUCT)
- `enterprise-key-derivation.mjs` now supplies independent, strictly validated **browser-only** key descriptors and reproducible non-extractable AES-256-GCM keys. Descriptors hold only `kind/version/tenantId/kdf/iterations/salt/cipher` and a random 16-byte salt. PBKDF2-HMAC-SHA-256 uses 600,000 iterations, domain-separated by tenant and protocol version. The caller supplies an exact passphrase of 16–256 characters; whitespace-only secrets are rejected. Passing the identical passphrase and descriptor recreates the key, while a different passphrase, tenant or salt does not decrypt the original artifact.
- This makes *local re-derivation possible in a separate authorized browser session*, **not** account password reset, server-side recovery, escrow, MFA, or a support-managed recovery service. The user must independently and safely preserve BOTH the descriptor and the original passphrase; loss of either can permanently destroy access to ciphertext. Minimum length is not a guarantee of resistance to dictionary attacks or stolen offline exports. Security/privacy review must approve passphrase entropy, KDF choices, key recovery UX, rotation, secure descriptor backup, and memory/session handling before any genuine user account is enabled.
- The module has no network or storage access and is barred from Worker imports by the no-deploy release gate; it is not connected to the old browser-local PBKDF2 vaults. No existing key, tenant or customer ciphertext has been migrated.
